# Server, Repo, and Database Spec

## Purpose

This document defines the current backend architecture for `sesUygulama`, focusing on:

- repository layout for server-side code
- server runtime responsibilities and contracts
- SQLite persistence model and invariants

It is intended as a maintenance spec for future refactors, bug fixes, and production hardening.

## Scope

This spec covers:

- [`server.js`](../server.js)
- [`server/`](../server)
- [`database.js`](../database.js)

It does not fully specify frontend rendering behavior in [`public/`](../public), except where the client depends on backend contracts.

## System Overview

The application is a single-process Node.js server with:

- `Express` for HTTP APIs and static asset serving
- `Socket.IO` for realtime chat, voice signaling, screen-share signaling, and poker state updates
- `SQLite` for durable persistence
- in-memory realtime maps for presence, voice room membership, active screen shares, and music queues

The backend is intentionally split into two layers:

1. durable state in [`database.js`](../database.js)
2. ephemeral realtime state in [`server/realtime-state.js`](../server/realtime-state.js)

## Runtime Responsibilities

### HTTP layer

The HTTP server is responsible for:

- serving static frontend files
- exposing auth endpoints
- exposing authenticated app bootstrap endpoints
- exposing authenticated SoundCloud search
- exposing a health endpoint

Current HTTP routes:

- `GET /health`
- `POST /api/auth/register`
- `POST /api/auth/login`
- `GET /api/auth/me`
- `POST /api/auth/logout`
- `GET /api/channels`
- `GET /api/client-config`
- `GET /api/music/search`

### Socket layer

The socket server is responsible for:

- channel join/switch lifecycle
- presence broadcasts
- chat message fanout
- DM delivery
- typing indicators
- voice room membership
- WebRTC signaling relay for voice
- WebRTC signaling relay for screen share
- music queue sync inside voice rooms
- poker table state and gameplay events

### Persistence layer

The persistence layer is responsible only for durable data:

- channels
- users/accounts
- auth token revocations
- channel messages
- message reactions
- direct messages

It is not responsible for:

- who is currently online
- who is in which voice room right now
- active WebRTC peers
- active screen shares
- current music playback state

Those remain process-local realtime state.

## Authentication Model

### Identity

Users authenticate with username + password against the `accounts` table.

### Password storage

Passwords are never stored in plaintext.

- hashing algorithm: `scrypt`
- stored format: `scrypt$<salt>$<hex-hash>`

### Session tokens

The app uses signed bearer tokens generated by [`server/auth.js`](../server/auth.js).

Token payload includes:

- `sub`: username
- `iat`: issued timestamp
- `exp`: expiry timestamp
- `jti`: unique token id
- `v`: token format version

### Revocation

Logout inserts the token `jti` into `revoked_tokens`. Both HTTP and socket auth must reject revoked tokens.

## API and Socket Contracts

### Auth bootstrap contract

After login/register, the client must:

1. store the bearer token
2. call `/api/auth/me`
3. call `/api/channels`
4. call `/api/client-config`
5. open the Socket.IO connection with `auth.token`

### Channel membership contract

A socket is not considered fully active until it emits `join` with:

- `channelId`
- `sessionId`

The server then:

- validates the token-backed user identity
- validates the channel
- records the connected user in realtime state
- emits message history and realtime snapshots

### Voice contract

Voice uses mesh-style peer connections:

- room membership is tracked by the server
- actual audio media flows peer-to-peer or via TURN
- the server only coordinates signaling and room membership

### Screen-share contract

Only one active screen share is allowed per text channel at a time.

The sharer is tracked by `channelId -> { sharerId, username }`.

### Music contract

Music state is scoped per voice room, not per text channel.

## Database Specification

### Engine

- backend: SQLite via `node:sqlite`
- mode: synchronous access inside a single Node process
- journaling: `WAL`
- foreign keys: enabled

### File paths

Default file resolution:

- legacy JSON: `chat-data.json`
- SQLite DB: `chat-data.sqlite`

Overrides:

- `SESAPP_DATA_FILE`
- `SESAPP_DB_FILE`

### Schema

#### `metadata`

Stores small key/value markers for migrations and app metadata.

Columns:

- `key TEXT PRIMARY KEY`
- `value TEXT NOT NULL`

#### `channels`

Stores durable text-channel definitions.

Columns:

- `id INTEGER PRIMARY KEY`
- `name TEXT NOT NULL`
- `description TEXT NOT NULL DEFAULT ''`

Seeded defaults:

- `genel`
- `oyun`
- `müzik`
- `duyurular`

#### `users`

Stores known usernames that may appear in messages/reactions.

Columns:

- `username TEXT PRIMARY KEY`

This acts as the shared identity base table for accounts and historical content.

#### `accounts`

Stores real login identities.

Columns:

- `username TEXT PRIMARY KEY`
- `password_hash TEXT NOT NULL`
- `created_at INTEGER NOT NULL`
- `last_login_at INTEGER NOT NULL`

Constraints:

- `username` references `users(username)`
- deleting a user cascades to the account row

#### `revoked_tokens`

Stores invalidated bearer tokens until expiry.

Columns:

- `token_id TEXT PRIMARY KEY`
- `revoked_at INTEGER NOT NULL`
- `expires_at INTEGER NOT NULL`

#### `messages`

Stores channel chat history.

Columns:

- `id INTEGER PRIMARY KEY AUTOINCREMENT`
- `channel_id INTEGER NOT NULL`
- `username TEXT NOT NULL`
- `content TEXT NOT NULL`
- `created_at INTEGER NOT NULL`

Constraints:

- `channel_id` references `channels(id)`

#### `message_reactions`

Stores per-user reactions on channel messages.

Columns:

- `message_id INTEGER NOT NULL`
- `emoji TEXT NOT NULL`
- `username TEXT NOT NULL`

Primary key:

- `(message_id, emoji, username)`

Constraints:

- `message_id` references `messages(id)`

#### `dms`

Stores direct messages between users.

Columns:

- `id INTEGER PRIMARY KEY AUTOINCREMENT`
- `from_user TEXT NOT NULL`
- `to_user TEXT NOT NULL`
- `content TEXT NOT NULL`
- `created_at INTEGER NOT NULL`

## Persistence API

The server relies on the following database operations:

- `getChannels()`
- `getChannelById(id)`
- `getMessages(channelId, limit?)`
- `insertMessage(channelId, username, content)`
- `toggleReaction(messageId, username, emoji)`
- `getDms(userA, userB, limit?)`
- `insertDm(from, to, content)`
- `ensureUser(username)`
- `getAccount(username)`
- `createAccount(username, passwordHash)`
- `touchAccountLogin(username)`
- `revokeToken(tokenId, expiresAt)`
- `isTokenRevoked(tokenId)`
- `close()`

## In-Memory Realtime State

The following state must remain process-local:

- `connectedUsers`
  - `socketId -> { username, channelId, sessionId }`
- `voiceRooms`
  - `roomName -> Map<socketId, { username }>`
- `screenShares`
  - `channelId -> { sharerId, username }`
- `musicState`
  - `voiceRoom -> { current, queue, isPlaying, startedAt, elapsed }`

This means the current architecture assumes a single active Node process for correctness.

## Operational Assumptions

### Single-process assumption

Because online presence and voice/screen/music state live in memory, the current system is designed for one app server instance.

If the app is scaled horizontally, a shared adapter/state layer such as Redis would be required.

### TURN / ICE

WebRTC connectivity depends on ICE server config from [`server/config.js`](../server/config.js).

Supported config styles:

- `RTC_ICE_SERVERS_JSON`
- `TURN_*` environment variables

### Deployment environments

The app supports:

- plain Node hosting
- Railway for web deployment
- Electron embedding for desktop packaging

## Invariants

These rules should remain true across future refactors:

1. A user account must exist before its token is accepted.
2. Revoked tokens must fail both HTTP and socket auth.
3. Realtime presence must not be reconstructed from the database.
4. Voice and screen-share media must never flow through the Node server itself.
5. Message history must remain durable across restarts.
6. Default text channels must always exist in an empty database.
7. Auth bootstrap must work with only a bearer token and no server-side session storage.

## Known Constraints

- SQLite access is synchronous, which is acceptable for the current small single-instance deployment model.
- Realtime state is not durable across process restarts.
- There is no built-in admin panel or migration framework yet.
- Poker state is not persisted and resets with process restarts.
